# 坐姿与书写手臂姿态检查

本机实时检查坐姿和书写手臂是否贴近一套可调整的姿势标准。浏览器打开摄像头，画面在本地用 YOLO 姿态模型取出人体关键点，再按肩、躯干、头和书写臂给出通过、接近或偏离。不上传画面，不判断身体前倾的深度，也不判断手指怎么握笔。

适合写进 proposal 的用法：一个人面对摄像头坐下，先把当前正确姿势记成标准，再在书写时看身体和手臂有没有离开这套标准。

## 能检查什么

检查分两块。

**坐姿**使用双肩、双耳、双眼、鼻，以及可靠时的双髋：

- 肩线相对水平的倾斜
- 躯干相对竖直的倾斜。双髋要离开画面边缘，髋宽和肩宽接近，并且髋在肩下方。桌子挡住髋时，这一项是无法判断，不是姿势错误
- 头相对肩线的左右偏移，用双耳中点；耳不够可靠时改用双眼中点。鼻子左右移动不算偏头
- 低头：鼻子到双眼连线的距离，除以眼距，向下为正。人只是靠近摄像头时，眼睛和鼻子一起变大，这个数基本不动

**书写手臂**使用书写侧的肩、肘、腕，在跟着肩线转正的坐标系里量。前臂更平、肘角更接近弯屈书写的那只手会被优先当成书写手；自动模式下，另一只手要连续三帧明显更高才切换。也可以手动指定左手或右手。腕相对书写肩按肩宽来量，画面右侧为正，向下为正。上臂或前臂短于约 0.18 个肩宽时，角度无法判断，因为手臂正对摄像头，平面角度不可靠。前臂和标准比的是不超过 180° 的转角差。

手指不在模型关键点里，因此这里只判断手臂摆放，不判断握笔松紧或笔杆角度。正面摄像头也看不清身体向前倾了多少。

## 标准怎么来

默认标准是端正坐姿：肩和躯干接近 0°，头在中线附近，低头约 0.7 个眼距，肘角约 105°，前臂接近水平，腕的标准在书写肩处。这个默认只是起点。旧版本里按肩宽保存的头高度不能换算，页面会另存一套参数，需要重新记录规范。

页面右侧一次列出全部可调参数。坐姿和书写各有一组标准和一组宽容，左右并排，同一行是同一部位。总宽容、缓冲、置信度、书写手、引导线、节点和画面调整放在操作条上。

记录规范、拖动空心圆、直接拖标准拉条，改的都是「正确姿势在哪」。单项宽容拉条改的是「离开多少仍可接受」。总宽容是一个倍数，默认 1：向右时每一项宽容一起放大，向左一起缩小，各项之间原来的比例保持不变。某一项设成 0 时，乘多少仍是 0。记录规范只覆盖标准，不改宽容度。

缓冲默认 5 秒。这几秒里只要出现过通过或接近，卡片结论就算通过。只有偏离一直持续到缓冲结束，结论才变成偏离。读数本身仍是当前这一帧，方便看出正在离开标准。

记录规范要先打开摄像头。画面从 5 倒数到 1，只平均倒数结束之后约 1 秒内拍下的姿势，写入肩线、躯干、头左右和低头。这一秒里有稳定书写手时，同时写入肘角、前臂和腕的位置。书写手为自动时，出现更多的那只手会被记下，手臂标准只按这只手计算。识别较慢时会等这一帧返回，不会把倒数期间的画面写进标准。仍然采不到，已有标准保持不动。

勾选「画面调整」后，可以拖画面上的空心圆。头左右的圆只沿肩线移动，低头的圆只沿眼睛连线的垂直方向移动，腕的圆在肩坐标系里移动。肘角和前臂用拉条或记录规范来定。

读数上，绿色表示在有效宽容度内，黄色表示刚超出，红色表示明显超出。有效宽容度是单项宽容乘上总宽容。读数旁的差是当前值减去标准。卡片上的通过或偏离还要再经过缓冲。关键点不够可靠时保持中性，不记为失败。

## 怎么看结果

画面按摄像头帧率播放，并做成镜像，方便对着自己调整。骨架、引导线和节点画在画面上，会比真实动作晚大约一次识别。引导线表示当前标准：肩线、身体轴线、头左右在肩线上的位置、低头在眼线垂直方向上的位置，以及从肘连到腕标准点的前臂。腕的空心圆就是腕在肩坐标系里的标准位置。

右侧两张卡片给出坐姿和书写手臂的结论，并附上肩、躯干、头、肘、前臂和腕相对标准的差，便于对照着改标准和宽容度。

## 实现

摄像头始终在浏览器里，画面按摄像头帧率播放。姿态估计有两种，由 `POSTURE_INFER` 决定：

- **client**：浏览器里用 MediaPipe lite，优先用显卡，按摄像头帧逐帧算。Render 的 Free 实例用这个模式。画面不上传。
- **server**：浏览器把宽边 640 的帧交给服务，用 YOLO26-pose 取最大的人。只适合本机或大内存 CPU。Free 实例放不下，帧率也低。

两种模式之后相同：

1. 平滑鼻、眼、耳、肩、肘、腕和髋。单帧飞点会丢掉，短暂丢失的点会保持约 0.3 秒。相邻两帧超过约 1 秒就重新开始平滑。
2. 按当帧提交的标准和宽容度计算坐姿与书写臂。
3. 浏览器把最近一次平滑后的关键点画回镜像画面。

服务端推理在 CPU 上运行，同一时间只处理一帧，并用这台机器的全部 CPU 线程跑这一帧。服务忙时新的帧会跳过，不会排队把页面卡住。标准保存在这台浏览器里，刷新后还在。

主要文件：

- `posture-web/index.html`：横向页面、摄像头、引导线和分组参数
- `posture-web/server.py`：姿态估计、坐姿和书写臂判断

## 本地运行

默认是 **client** 模式：页面用浏览器里的 MediaPipe 估姿态，本机服务只负责托管 `index.html` / `score.js`。在仓库根目录：

```text
.\.venv\Scripts\python.exe posture-web\server.py
```

浏览器打开 <http://127.0.0.1:8765>。需要摄像头权限；首次打开会从 CDN 拉 MediaPipe WASM 与 lite 模型。

若仍要用服务端 YOLO（本机已装 ultralytics 时）：

```text
$env:POSTURE_INFER = "server"
.\.venv\Scripts\python.exe posture-web\server.py
```

服务端模式默认下载 `yolo26n-pose.pt`。需要先装 CPU 版 PyTorch，再 `pip install -r posture-web\requirements-server.txt`（或现有 `.venv`）。线上 Render 不用这个模式。

其它环境变量：`PORT`、`HOST`、`POSTURE_IMGSZ`（server 默认 640）、`POSTURE_THREADS`（默认用满 CPU）、`POSTURE_PRELOAD`（仅 server）。`/config` 告知前端模式；`/healthz` 在模型未就绪时返回 503。

## 部署到 Render

线上用 **Free** 和 **`POSTURE_INFER=client`**。姿态在浏览器里用 MediaPipe lite 逐帧计算，优先走显卡。Render 只托管页面，不跑 PyTorch。帧不用上传，所以识别能跟上摄像头，而不是服务器上 `yolo26l-pose` 那种一两帧每秒。

Free 大约 512MB、0.1 个 CPU，放不下 YOLO。空闲约 15 分钟后实例会休眠，下次打开先等几秒唤醒，再从 CDN 加载一次模型。

用仓库根目录的 Blueprint（`render.yaml`，`plan: free`）。手工建服务时：

1. New → Web Service，接上含 `posture-web/` 的仓库，分支 `feat/posture-web-render`。
2. Root Directory 填 `posture-web`。
3. Instance 选 **Free**。
4. Build Command：`pip install -r requirements.txt`（不要装 `requirements-server.txt`）。
5. Start Command：`gunicorn --bind 0.0.0.0:$PORT --workers 1 --threads 2 --timeout 60 server:app`
6. Health Check Path：`/healthz`
7. 环境变量：`PYTHON_VERSION=3.12.8`，`POSTURE_INFER=client`，`POSTURE_PRELOAD=0`

## 写 proposal 时建议守住的边界

- 这是单人、本机、实时的姿态反馈原型，不是课堂监控，也不是医疗评估。
- 书写部分评价的是肩、肘、腕组成的手臂姿势，不能写成手指握笔识别。
- 标准由使用者自己记录或拖动设定，系统没有内置一套临床上的「正确坐姿」或「正确握笔」。
- 侧身、出画、遮挡或关键点置信度不够时，对应项目会显示无法判断，而不是判为错误。髋被桌子挡住时，躯干同样是无法判断。
- 不测量身体前倾。低头只表示脸相对眼睛低下去，不是躯干在深度上前倾。
- 本机 client 模式里，画面和识别都留在这台电脑。Render 的 server 模式会把缩小后的 JPEG 帧发到服务器，proposal 里不要写成数据不出本机。
